## What kind of construction this is

A hybrid (ECIES-style) scheme: an ephemeral-key Diffie-Hellman-like key agreement over a twisted
Edwards curve, feeding a derived value into a symmetric block-cipher stage (DSTU 7624:2014 —
Kalyna — used in what the thesis calls **KIVREP** mode, expanded in the acronym list as "Key
IV-based Reversible Encryption Process"; the abbreviation is stated but the mode's own internal
construction is not — see "Open gaps" below). Kupyna (DSTU 7564:2014) is the recommended hash for
the confirmation tag baked into the plaintext padding (step 7/8 below). Two versions of the
algorithm appear in the source, described next.

## Notation (Section 1.2)

- `M` — the message to encrypt; `l(M)` — its length in bits.
- `P = (x_P, y_P)` — the curve's base point; `n` — its order (a prime, odd number).
- `e` — the recipient's private encryption key, integer, `1 < e < n - 1`.
- `ε` — the one-time (ephemeral) encryption key, secret integer, `1 < ε < n - 1`.
- `Q = eP` — the recipient's public encryption key, `(x_Q, y_Q)` its coordinates.
- `u || v` — concatenation of bit strings.
- `H` — the hash function; `l_H` — its output length; `H(M)` — hash of `M`.
- `i_H = (0, i6, ..., i0)` — the hash function's identifier (a 7-bit tag plus a leading `0`).
- `p` — the prime defining the base field `F_p`, sized so `l(p) = 2(λ + 1)` where `λ` is the
  target security level (attacker needs `2^λ` operations).
- `E^(κ)_{l,k}(M)` / `D^(κ)_{l,k}(M)` — Kalyna-l/k-KW or Kalyna-l/k-KW-p forward/inverse transform,
  block length `l` bits, key `κ` of length `k` bits, in KIVREP mode.

## Encryption algorithm (Section 1.2, first form)

```
Input:  general encryption parameters; public encryption key Q; message M, l(M) > 0;
        hash-function identifier i_H; Kalyna-l/k-KW(-p) block length and key length.
Output: ciphertext C, or an error.

1)  Validate the general encryption parameters; on failure: "Invalid general parameters", abort.
2)  Compute l(M); require 0 < l(M) <= l_max(p).
    if l(M) == 0:        "Message is empty", abort.
    if l(M) > l_max(p):  "Message length exceeds maximum", abort.
3)  M~ = M.
4)  if l(M) < l_max(p): pad M~ to fixed length l_max(p) (M~ = (m_l, ..., m_0)).
5)  Convert the integer l(M) to a bit string.
6)  Convert that bit string to a fixed-length-16 bit string l_M~(16).
7)  Compute H(l_M~(16) || M~) = (h_{l_H}, ..., h_0) using the hash function named by i_H,
    with p determining l_H (the hash's output length).
8)  Build M' = i_H || H(l_M~(16) || M~) || l_M~(16) || M~.
9)  Compute the one-time encryption key ε.
10) Compute the curve point R = εP = (x_R, y_R).
11) r = x_R, converted to a bit string of length l(p).
12) Compute the curve point T = εQ = (x_T, y_T).
13) κ = x_T (truncated/used as the k-bit key for the block-cipher stage).
14) t = E^(κ)_{l,k}(M').
15) Output ciphertext C = (r || t).
```

## Decryption algorithm (Section 1.2, first form)

```
Input:  ciphertext C = (r || t); private key e; general parameters.
Output: message M, or an error.

1)  Determine l_H from p.
2)  if r == 0, or r == 1, or r^2 == a*d^-1 mod p: "Ciphertext is invalid", abort.
3)  v = (1 - r^2) * (a - d*r^2)^-1 mod p.
4)  δ = v^((p-1)/2) mod p. if δ == p - 1: "Ciphertext is invalid", abort.
5)  y = sqrt(v) mod p.
6)  R' = (r, y).                                     // reconstructs the point from its x-coord
7)  T' = e * R'.                                     // [AMBIGUITY — see below] source literally
                                                      // writes "T' = e*r" (scalar r, not point R')
8)  κ = x_T'.                                        // [AMBIGUITY] source writes an inconsistent
                                                      // superscript here vs. encrypt step 13 — read
                                                      // as the same x_T truncation either way
9)  Compute (u_{l(p)-1}, ..., u_0) = D^(κ)_{l,k}(t).
10) i_H = (u_{l(p)-1}, ..., u_{l(p)-8}); verify it names a hash function valid for this user
    group. On failure: "Invalid hash-function identifier", abort.
11) Look up the hash function H named by i_H.
12) Compute l_max(p).
13) l_M~ = (u_{l_max(p)+15}, ..., u_{l_max(p)}).            // [source has a typo'd subscript here]
14) l(M) = sum_{i=0..15} u_{l_max(p)+i} * 2^i, read from l_M~.
15) M' = (u_{l_max(p)+15}, ..., u_0), read from (u_{l(p)-1}, ..., u_0).
16) Verify H(M') == (u_{l_max+l_H+15}, ..., u_{l_max(p)+16}).
    On mismatch: "Invalid hash-function value", abort.
17) b = l_max(p) - l(M). if b != 0: verify (u_{l_max(p)-1}, ..., u_{l(M)}) == all-zero padding.
    On mismatch: "Invalid message value", abort.
18) M = (u_{l(M)-1}, ..., u_0).
19) Output M.
```

## Encryption/decryption algorithm (Section 2.1.1, second, simplified form)

The thesis restates the same construction in a plainer Diffie-Hellman-style framing while setting
up its own attack analysis — worth keeping alongside the form above since it cross-confirms the
overall shape (ephemeral key, curve-point-derived symmetric key, one block-cipher call) even
though it elides the padding/hash/identifier machinery of steps 5–9 and 13–17 above:

```
Setup: Alice's private key h, 2 <= h <= q-2; public key H = hP. Curve subgroup order q.

Encrypt (Bob, using Alice's public key H):
1) Pick random ε, 2 <= ε <= q-2. Compute R = εP = (x_R, y_R).
2) r = x_R.
3) Compute T = εH = (x_T, y_T).
4) t = x_T.
5) u = E_t(M)                       // symmetric cipher, e.g. DSTU 7624:2014
Ciphertext: (r, u), sent together with the base point εP.

Decrypt (Alice, using private key h):
1) Compute T = h * (εP)             // [AMBIGUITY] source literally writes "T = hP" here — that
                                     // reads as reconstructing Alice's own public key, which is
                                     // ciphertext-independent and cannot be what's meant; the
                                     // surrounding prose ("obtains hεP using private key h and
                                     // base point P") implies εP (i.e. R, reconstructed from r)
                                     // is the actual second operand, not P itself
2) t = x_T
3) M = D_t(u)                       // symmetric-cipher inverse
```

**This is the same shape of slip as decrypt step 7 in the first form above** (a scalar-times-point
step written with the wrong point operand) — appearing independently, in a differently-phrased
section of the same document. That repetition is worth noting explicitly: it reads as a genuine
error in the author's own working notation, not a copy-paste artifact of this transcription — but
"reads as" is still not a citable confirmation, so both instances stay flagged, not silently fixed.

## Open gaps (not answerable from this source alone)

- **`l_max(p)` is never given a formula.** Both algorithms above compute or reference it multiple
  times, but the thesis states only that it's "computed from `p`" — never the actual relationship
  (presumably something like `l(p)` minus the hash-output, identifier, and length-prefix field
  widths, by analogy with how those fields are packed into `M'` in step 8, but that is this
  project's own inference, not a transcribed fact).
- **The curve parameters `a`, `d`, `p` themselves are never given** — no recommended curve, no
  worked numeric example (unlike `DSTU_4145-2002.pdf` Annex Б for the signature standard). Decrypt
  step 3's `a - d*r^2` formula confirms the curve equation form (`x² + a·y² = d·x²y² + 1`, per
  Definition 1.1) but not which concrete `(a, d, p)` triple the standard mandates.
- **KIVREP itself is never defined beyond the acronym expansion** ("Key IV-based Reversible
  Encryption Process") — how it relates to, or differs from, the Kalyna modes already implemented
  in this project (`hazmat::kalyna_kw`/`kalyna_ecb`/etc.) is not stated.
- **The hash-identifier encoding (`i_H`'s 7 meaningful bits) and "user group" concept** (step 10 of
  decryption) are referenced as existing conventions without being defined — likely cross-references
  to a DSTU 7564:2014 or DSTU 9041:2020 registry this thesis assumes the reader already has.

None of these gaps block writing this pseudocode document (its job is to state what the source
says, ambiguities included) — they block treating this as implementation-ready, which is the
point: see the provenance warning at the top.
