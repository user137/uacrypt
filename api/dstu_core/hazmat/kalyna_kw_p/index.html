Module kalyna_kw_p 

Source
Expand description

Kalyna-KW-p: DSTU 7624:2014 §15.4/15.5, key wrap with padding, for a message whose length is not a multiple of the block (T-253, docs/DECISIONS.md D-241/D-243). A block-aligned message is plain KW’s case (§15.1), super::kalyna_kw.

Wrap (§15.4): M || μ_{l/2}(|M|) - the bit length as a half-block little-endian field - then annex Б.2’s padding (a 1 bit, here the byte 0x80, then zeros up to a block; Б.2 always pads, a full block when the data is already aligned), then KW (§15.2), which appends the all-zero checksum block. Unwrap (§15.5): KW, then Б.3 (drop the trailing zeros and the 1 bit), then the last half block must equal μ_{l/2} of the length that remains.

§Deviations from the reference implementations, not from the text

UAPKI’s padding() pads only unaligned data, so for |M| + l/2 a multiple of the block it produces a different ciphertext from §15.4 (this is the DSTU 9041 l(p)=384 case, D-241); its decrypt_kw strips trailing zero bytes and never checks the length field. Bouncy Castle has no padded mode. This module follows the text.

Unwrap is strict and constant-time over the recovered block: the 1 bit must be the byte 0x80 (this is a byte API), the length field must be exactly μ_{l/2}(8·L) with its unused top bytes zero, the padding must be the minimal Б.2 padding, and L must be a length wrap accepts (L > l, not a multiple of l). Any failure, the KW checksum’s included, is the one KwError::ChecksumMismatch, and out is zeroed: no padding oracle, one encoding per message.

Do not use this for new designs without a specific, understood reason - the same raw key-wrap caveat as super::kalyna_kw. No heap allocation; inputs are bounded by KW’s 20-block limit.
