crypto_box equivalent at l(p)=512 (E512/1, docs/TASKS.md T-193) - direct sibling of crate::crypto_box (l(p)=256, T-178) at this curve size’s own widths. Matches this project’s established per-curve-size sibling-module precedent (hazmat::dstu9041::curve512 etc., D-181), not a generic-over-width merge.

§Seed width - fixed at 32 bytes, not l(p)=512’s full 424-bit KEM capacity

crypto_box’s own embed_seed (l(p)=256, SEED_LEN = L_MAX_P/8 = 25) does not generalize here: l(p)=512’s L_MAX_P = 424 bits (53 bytes) exceeds Kupyna256Kdf’s 32-byte input width, so a literal copy-paste underflows. docs/DECISIONS.md D-182 resolved this: the seed stays a fixed 32 bytes (the stream-key derivation’s own native key width - originally Kupyna256Kdf, Kupyna256Kmac since T-248 - no embedding/padding step needed at all), wrapped via dstu9041_encrypt(&seed, 256, ...) (message_bits fixed at 256, not L_MAX_P). open requires the recovered bit length to be exactly 256 before trusting the recovered seed - confirmed against message512.rs directly (not assumed) that decrypt genuinely returns the encryptor-supplied bit length, not the buffer’s fixed width (D-182). Leaving most of L_MAX_P’s 424 bits of KEM capacity unused is deliberate: the seed only ever needs to reach that derivation’s fixed 32-byte key input, matching crypto_box’s own “asymmetric step only ever establishes key material” framing.

§PublicKey is 64 bytes - the curve point’s x-coordinate only

Independently re-derived for E512/1 rather than assumed to carry over from crypto_box’s own l(p)=256 argument (this project’s standing “don’t assume a security argument carries over unchecked” discipline, D-176/D-178’s own precedent): the compression-safety argument is a curve-family property (twisted Edwards negation -(x,y) = (x,-y) in this standard’s own swapped-Edwards convention), not a p/d/n-value-dependent one, so it holds identically for E512/1 - x_T = x_{-T} for any point T, hence k*(-Q) = -(k*Q) gives the same kappa = x_{epsilon*Q} regardless of which square-root branch crate::hazmat::dstu9041::curve512::point_from_x returns. PublicKey::from_bytes reuses that function’s own rejection gauntlet directly, not a second copy.

§Error collapsing, wire format

Same posture as crate::crypto_box - OpenError deliberately does not distinguish a KEM failure from a secretstream tag failure (D-56/D-63 precedent); only OpenError::Truncated and OpenError::UnsupportedVersion stay separate. Wire format (version 3, T-265/D-239): version (1 byte, 3) || dstu9041_ciphertext (256 bytes) || <D-208 stream file>, written and read by seal_stream/open_stream (bounded memory) or seal/open (one call); the one-chunk version 2 of 0.4-0.6 is read only by open_v2_legacy. The stream key is Kupyna256Kmac(key = seed, message = b"cryptbx5" || version || kem_ciphertext || recipient_public_key) - the same RFC 9180 §4.1 kem_context binding as crate::crypto_box (T-248, docs/DECISIONS.md D-201).

A box-open-length-valid l(p)=512 sealed blob also clears crate::crypto_box::open’s own minimum-length check (183 bytes) - it falls through to its own InvalidCiphertext/authentication-failure path rather than a distinct “wrong curve size” error. Defensible under the shared error-collapsing posture (recorded here, not left to be found by surprise): a curve-size mismatch is just another way for the KEM decrypt to fail.

§Provenance

Not itself DSTU-specified, like crypto_box - no vector oracle exists or ever will for this composite; verified by property/tamper/misuse tests only (tests/crypto_box512.rs). hazmat::dstu9041::encryption512 itself remains verified against Додаток Г.3 (T-192).

Functions§

open
Decrypts sealed (as produced by seal or seal_stream) under secret - the in-memory form of open_stream. Partially decrypted plaintext is zeroized before an error returns.
open_stream
Starts opening a message sealed by seal or seal_stream (T-265): prefix is its first OPEN_STREAM_PREFIX_BYTES bytes. Feed the returned FileDecryptor everything after them, as the stream-file codec documents: a record’s plaintext comes out only once it verifies, the Final record’s only from finish, once the input is known to end there.
open_v2_legacy
Decrypts a blob in the one-chunk format 0.4-0.6 wrote (version byte 2: version || kem ciphertext (256) || secretstream header (32) || ciphertext || tag (16)). It exists for uacrypt box-open, which still opens files sealed before T-265 (owner decision 2026-10-15, D-239); it is not memory-bounded and not wired into the C ABI or any binding. seal never writes this format.
seal
Encrypts message (any length) to recipient, drawing a fresh random seed and ephemeral key internally - see the module doc’s “Seed width” section. The in-memory form of seal_stream; the result is sealed_len(message.len()) bytes.
seal_stream
Starts sealing a message of any length to recipient as a stream (T-265): returns the FileEncryptor for its records and the SEAL_STREAM_PREFIX_BYTES-byte prefix to write first. Drive the encryptor as the stream-file codec documents (every full CHUNK_BYTES chunk with seal_chunk, the last 0..=CHUNK_BYTES bytes with seal_final); the bytes are then exactly what seal returns, and open/open_stream read them. The stream key never leaves the library.
sealed_len
The exact length seal returns for a message_len-byte message, or None if it overflows usize: the prefix, the message, and one record overhead per started CHUNK_BYTES chunk - at least one, since an empty message is one empty Final record.
